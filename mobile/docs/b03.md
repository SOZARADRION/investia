# B03 — perfil mínimo no Firestore

## Implementação em 06/11/2026 — fluxo principal validado no Android

O Perfil agora oferece Carregar perfil e Salvar nome para contas com e-mail
verificado. As operações são explícitas, sem listeners contínuos. A leitura
exige resposta do servidor; a gravação usa transação com serverTimestamp e
preserva createdAt. O nome é aparado e limitado a 80 caracteres. O nome do
Authentication não é alterado. Nenhum perfil é criado automaticamente.

O usuário confirmou no Android: ausência inicial de perfil; criação; recuperação
do nome salvo após alterar o campo sem salvar; atualização; leitura após fechar
e reabrir o Expo Go; mensagem de conexão ao salvar sem rede; reconexão e leitura
do valor anterior, sem alteração pela tentativa offline. Uma segunda conta
verificada não encontrou perfil inicial, salvou outro nome e, ao voltar à
primeira conta, o nome original foi recuperado. Nenhum e-mail pessoal foi
incluído neste registro.

TypeScript e lint passaram na implementação. Os testes de autorização do
emulador descritos abaixo são anteriores; não foram reexecutados nesta etapa.
O usuário também confirmou no Android que um nome composto só de espaços
desativa Salvar nome e que uma conta não verificada mostra Confirme seu e-mail,
sem o cartão Meu perfil salvo. A matriz manual planejada desta etapa foi
concluída; isso não substitui os testes de autorização das regras.

Referências de implementação: documentação Firebase de transações e leitura
de documentos (https://firebase.google.com/docs/firestore/manage-data/transactions
e https://firebase.google.com/docs/firestore/query-data/get-data).

## Escopo

Documento único `users/{uid}` para cada conta, sem consultas de listagem:

| Campo | Tipo | Regra |
| --- | --- | --- |
| `displayName` | string | Entre 1 e 80 caracteres; aplicação deve aparar espaços |
| `createdAt` | timestamp | Timestamp do servidor na criação; imutável depois |
| `updatedAt` | timestamp | Timestamp do servidor em cada gravação |

Nome do perfil não é um papel de autorização. E-mail, senha, tokens,
informações bancárias e dados financeiros não serão copiados para o perfil.
Chat, Simulador, FastAPI e IA permanecem fora desta entrega.

## Autorização preparada

Fonte: `firebase/firestore.rules`, na raiz do repositório.

- Leitura de documento individual, criação e atualização somente pelo próprio
  UID, com token Firebase que indique e-mail verificado.
- Listagem de usuários, exclusões, campos extras e demais coleções negados.
- Criação e atualização exigem formato completo e timestamps do servidor.
- Nenhuma chave administrativa no aplicativo.

Essas condições só entram em vigor após publicação e validação das regras.
O console e ferramentas administrativas têm permissões diferentes das do SDK
cliente; visualizar documentos no console não prova isolamento entre contas.

## Matriz de testes de autorização

Usar simulador de regras ou emulador com identidades fictícias diferentes.
Não concluir segurança de isolamento somente pelos testes visuais no Android.

| Caso | Resultado esperado |
| --- | --- |
| Sem autenticação tenta ler/gravar | Negado |
| Conta A não verificada acessa `users/A` | Negado |
| Conta A verificada lê `users/A` | Permitido |
| Conta B verificada lê/grava `users/A` | Negado |
| Conta A cria perfil válido com timestamps do servidor | Permitido |
| Conta A inclui `role`, `email` ou outro campo extra | Negado |
| Conta A altera `createdAt` | Negado |
| Conta A grava nome com tipo/tamanho inválido | Negado |
| Conta A lista a coleção `users` ou exclui perfil | Negado |
| Acesso a outra coleção | Negado |

Também conferir no Android: perfil não criado, criação única, edição,
persistência ao reabrir, troca de conta sem dados anteriores, falta de rede
e conta não verificada. Esses testes ainda não foram executados.

## Testes automáticos isolados

Arquivos em `firebase/tests/`, executados pelo workflow Firestore rules.
O projeto emulado é `demo-investia`, sem credenciais e sem vinculação ao
projeto real. Os testes interrompem a execução caso não encontrem o emulador
local e o ID fictício. Não há comando de deploy no workflow.

Para execução local, é necessário Node 24 e Java 21. Na pasta `firebase`,
executar `npm ci` e `npm test`. No notebook atual, optou-se pela execução no
GitHub para não instalar outro runtime nem carregar a máquina.
